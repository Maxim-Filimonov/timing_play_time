# Playtime

Converts real-world time spent on worthwhile activities (tracked in the Timing app) plus manually-synced exercise time into a balance of earned play time, which is spent down by logging play sessions.

## Language

**User**:
The tenant boundary. Owns Activities, the Play Balance, an Integration, a timezone, and optionally a Linked Email. Identity is an anonymous, long-lived session cookie (see [ADR-0006](docs/adr/0006-multi-tenant-anonymous-cookie-accounts.md)); `users.id` is the sole identity and nothing foreign-keys to anything else. A User may optionally attach one verified Linked Email for cross-device access and recovery from cookie loss (see [ADR-0015](docs/adr/0015-optional-email-linking-via-auth0-passwordless.md)) — the identity join key for that is `auth0_sub`, not the email. Without a Linked Email, losing the cookie still means losing access to that User's data. There is still no logged-out state: clearing the cookie silently provisions a fresh empty User, not a login screen.
_Avoid_: Account, tenant (User is this app's term; "account" carries connotations — billing, roles, a mandatory credential — that still don't apply, even though an optional Linked Email now can)

**Linked Email**:
An email address a User has optionally attached to their identity, for cross-device access and recovery from session-cookie loss (see [ADR-0015](docs/adr/0015-optional-email-linking-via-auth0-passwordless.md)). Opt-in from Settings; verified once via an Auth0 passwordless Login Code. Stored on the User as a denormalised display copy (`email`) beside `auth0_sub` — the real identity join key — and never used for lookup. Once attached it is **permanent**: v1 has no in-app unlink and no in-app change-email, because Auth0 cannot change the email on a passwordless identity (a different address is a different `auth0_sub`, hence a different User under the switch-never-merge collision policy). An email already attached to another User is refused, not transferred. Surfaced only as a read-only masked status line in Settings; re-synced from the Auth0 identity (same `auth0_sub` only) on each login.
_Avoid_: Account email, login email (it is a recovery credential, not a username — the app still has no username); verified email (verification is a one-time gate, not a stored attribute)

**Login Code**:
The one-time numeric code Auth0 emails during a link or sign-in flow, entered on Auth0's hosted Universal Login page — never in this app's own UI (see [ADR-0015](docs/adr/0015-optional-email-linking-via-auth0-passwordless.md)). A code rather than a magic link because the flow's purpose is cross-device: a link mailed to a phone opens on the phone — the device you are signing in *from*, not *to* — whereas a code is transcribable across devices. Validity, single-use, and attempt limits are Auth0's to enforce, not this app's.
_Avoid_: Magic link (deliberately not used), OTP (Auth0's term — Login Code is this app's), verification code

**Integration**:
A User's connection to one external time-tracking provider at a time — Timing or RescueTime, never both at once (see [ADR-0016](docs/adr/0016-rescuetime-second-time-source-with-runtime-adapter-dispatch.md)) — holding provider-specific encrypted credentials (see [ADR-0007](docs/adr/0007-generic-per-user-integration-credentials.md)). Replaces what was previously a single global Timing API key shared by the whole app. Which provider's `TimeSource` adapter answers a given call is resolved per-User at runtime (`TimeSource.for/1`), not fixed for the whole running app.
_Avoid_: Connection, provider config

**Activity**:
A category of task that earns Play Minutes when time is logged against it. Maps 1:1 to a Source (below) by id — scoped to the owning User's Integration, since each User now connects to their own account — and carries a Multiplier, an Effect, and an Activated At timestamp. An Activity whose Effect is negative is a **Draining Activity**: time tracked against it subtracts Play Minutes instead of adding them (see Effect). Activated At still bounds which entries count toward the debug-only Timing-Derived Earned Total (below), but is purely descriptive — not load-bearing — for the user-facing User Displayed Total, which uses a fixed rolling window instead (see User Displayed Total).
_Avoid_: Task, Chore, Project (Project is Timing's term for one kind of Source; Activity is this app's wrapper around a Source with a multiplier attached)

**Source**:
The external tracked entity an Activity maps to — a Timing Project or, as of [ADR-0016](docs/adr/0016-rescuetime-second-time-source-with-runtime-adapter-dispatch.md), a RescueTime Activity (RescueTime's own term for one tracked app/website; its Category becomes the Source's sole `ancestors` entry) — the mapping runs through the `TimeSource` plugin boundary ([ADR-0002](docs/adr/0002-microkernel-plugin-architecture.md)), not tied to either provider. In the Add/Edit Activity forms the user picks one from a hierarchical picker that lists Sources via the `TimeSource.list_sources/1` capability ([ADR-0014](docs/adr/0014-hierarchical-source-picker-and-list-sources-capability.md)), flattened to a pre-order path list (parent then subtree, alphabetical within a level). The chosen Source's id is stored bare in `time_source_identifier`; its flattened path label (`"Edu → Coding"`) is snapshotted at pick time into `time_source_label` and never auto-refreshed, so a later upstream rename or deletion doesn't change what the user picked. When the list can't be loaded (no Integration, or the fetch fails) the picker falls back to a plain "enter the id by hand" field.
_Avoid_: Timing Project (Timing's name for one kind of Source — the field and the domain term are provider-neutral), Project

**Multiplier**:
A positive decimal magnitude (may be below or above 1) attached to an Activity, applied to minutes spent to compute how many Play Minutes that time is worth. It carries no direction of its own — whether that worth is added to or subtracted from the balance is the Activity's Effect (below). Configured per Activity in the persistence backend, not hardcoded; 0 is refused, since an Activity that neither earns nor drains is noise on the dashboard.
_Avoid_: negative multiplier (direction lives in Effect, not in the Multiplier's sign — see [ADR-0013](docs/adr/0013-draining-activities-outside-the-consumption-ledger.md))

**Effect**:
An Activity's direction: **positive** (time tracked against it earns Play Minutes) or **negative** (time tracked against it subtracts them). Stored on the Activity in its own right rather than derived from the Multiplier's sign, so the Multiplier stays a pure magnitude and the same shape holds for an Activity and for the Timing entries built from it (see [ADR-0013](docs/adr/0013-draining-activities-outside-the-consumption-ledger.md)). An Activity with negative Effect is a **Draining Activity** — the motivating case being time spent watching YouTube, which should cost play time rather than earn it. Changing an Activity's Effect applies to the whole Entry Expiry Window immediately, not just to time tracked afterwards, so the UI confirms the projected deduction whenever an Activity crosses into negative Effect.
_Avoid_: sign, polarity, penalty (Effect is the attribute; "Draining Activity" is the shorthand for a negative one)

**Play Minutes**:
The unit of play time. Computed from Activities (minutes spent × Multiplier, added or subtracted according to the Activity's Effect) or reported directly via a Manual Sync. Also shown per-Activity scoped to just today (the local calendar day, per [ADR-0005](docs/adr/0005-local-timezone-for-day-boundaries.md)) alongside the raw Timing minutes it was computed from — a live day-scoped view of the same computation as User Displayed Total, not a separate stored figure. (Today is always within the Entry Expiry Window, so this view is unaffected by expiry in practice.)

**Timing-Derived Earned Total**:
The live-computed, all-time sum of (entry duration × Multiplier) across every entry the connected provider reports on each Activity's mapped Source, counting only entries from the beginning of the calendar day (UTC) containing the *earliest* Activated At timestamp across the User's Activities onward — one shared cutoff applied to every one of that User's Activities, not a separate cutoff per Activity. This means an Activity activated after another of the User's Activities can retroactively earn for entries logged before it existed, as long as they fall after the earliest Activity's cutoff (see [ADR-0008](docs/adr/0008-shared-earliest-activation-cutoff-for-batched-timing-fetch.md)) — a deliberate precision-for-efficiency trade-off, made so all of a User's Activities can be fetched in a single batched call instead of one call per Activity. Recomputed fresh each time it's shown — not a stored ledger, so editing an old entry or changing an Activity's Multiplier changes this total retroactively. For a RescueTime-backed User, "all-time" silently degrades to whatever the RescueTime Lite tier's 2-week server-side history cap will return (see [ADR-0016](docs/adr/0016-rescuetime-second-time-source-with-runtime-adapter-dispatch.md)) — a known, accepted provider-specific limitation on this debug-only figure. **Debug-only**: as of the Entry Expiry Window decision, this unbounded figure powers only the debug-only Play Balance reveal (triple-tap the joystick icon); every user-facing figure (Playtime, Today's PT, Reserve) uses User Displayed Total instead, which comfortably fits inside the 2-week cap either way.

**Entry Expiry Window**:
The rule that a Timing entry stops counting toward User Displayed Total once more than 7 days have passed since the entry's own `start_date` — an exact rolling timestamp cutoff (`now − 7 days`), re-evaluated on every read, not aligned to local calendar days. Applies only to Timing entries; Pushscroll Balance (a Manual Sync value) is exempt, since it has no per-entry timestamp to decay against. Deliberately makes Reserve shrink over time even with no new Playtime Used logged against it — the intended effect, to keep a standing Reserve from removing the incentive to keep doing Activities.

**Entry Consumption Ledger**:
The per-entry FIFO record of how much of each Timing entry's earned minutes remain unspent. A logged Playtime Used spend draws down entries in two passes, preserving Today's PT's existing "resets fresh every local day, no exceptions" rule: first, consume today's own entries (today's local calendar day, per [ADR-0005](docs/adr/0005-local-timezone-for-day-boundaries.md)); only if the spend exceeds what's available there does it spill into Reserve's entries still inside the Entry Expiry Window, oldest-`start_date`-first among those — never into Backlog (see [ADR-0012](docs/adr/0012-persisted-entry-consumption-ledger-with-window-bounded-spending.md)). Each entry's `remaining` balance drops as it's consumed. An entry's `remaining` (not its original earned amount) is what the Entry Expiry Window acts on — once `remaining` reaches 0 (fully spent) an entry's later expiry has no effect, since there's nothing left on it to lose. A spend is refused outright — nothing logged, nothing consumed — if the User has no timezone yet (the two-pass draw-down needs a local day boundary, per [ADR-0005](docs/adr/0005-local-timezone-for-day-boundaries.md)) or if the Timing fetch fails, since settling a spend against an empty pool would book it as a permanent, self-uncorrecting deficit. As of ADR-0012, the *consumed* portion is persisted (one `EntryConsumption` row per entry actually drawn on, keyed per-User by `{User, Activity, Timing entry}` and frozen in Play Minutes at spend time) rather than recomputed live — the one deliberate exception to this app's "recomputed fresh, not stored" pattern, needed because a live replay was silently forgetting consumption once the spend that caused it aged past the window. An entry's *total earned* amount stays live-derived from the Activity's current Multiplier, same as always; only what's been spent from it is fixed. Entries belonging to a Draining Activity never enter this ledger at all: they are never consumed, never drawn down, and never produce a consumption row — they simply sum in negatively (see [ADR-0013](docs/adr/0013-draining-activities-outside-the-consumption-ledger.md)). Because a drain is never drawn down, it sits at full weight for its whole 7 days and then leaves the Entry Expiry Window like any other entry: a bad week is behind you in a week, and a drain can be waited out rather than worked off.

**Spend Receipt**:
A per-Activity breakdown of which Activities' entries funded a given Playtime Used spend, derived from the Entry Consumption Ledger's draw-down at the moment that spend is displayed. Always shown alongside the logged spend — even when a single Activity funded 100% of it — rather than only appearing for multi-Activity spends, so the UI element is predictable rather than one that intermittently appears.

**User Displayed Total**:
The Timing-derived earned total actually shown to the user, via Playtime and Reserve: the sum of each Timing entry's `remaining` balance (Entry Consumption Ledger, above), for every entry still within the Entry Expiry Window (the last 7 days from `now`), across every one of the User's Activities — one shared fixed cutoff, not scoped per Activity, and not bounded by any Activity's Activated At. Recomputed fresh each time it's shown, the same as Timing-Derived Earned Total, but bounded to a rolling week and ledger-aware rather than a raw all-time sum. Because expiry only removes *unspent remaining* balance, this can never go negative from expiry alone — it's exactly the earned-but-not-yet-spent minutes still inside the window, no more, no less.

**Manual Sync**:
An absolute total of Play Minutes, entered by hand from an external source (currently Pushscroll, an iOS app with its own earn/spend economy — no API, so syncing is manual). Each sync overwrites the previous Manual Sync value — it does not add to it, because the number entered is already Pushscroll's own net balance, not a delta. Displayed to the user as "Pushscroll Balance" in the UI — "sync" is developer jargon, and "Exercise Minutes" undersold that the figure is bidirectional (Pushscroll's balance rises when the User exercises and *falls* when they spend it on Pushscroll-tracked apps); only the label differs, the underlying replace-not-add semantics are unchanged. A drop in Pushscroll Balance lowers Reserve (see below) by design — spending time on a Pushscroll-tracked app costs Play Minutes the same way logging Playtime Used does, just through a different app's accounting.
_Avoid_: Sync delta, sync amount (it's a replace, not an increment); Exercise Minutes (implies one-directional, exercise-only growth)

**Playtime Used**:
A logged expenditure of Play Minutes (minutes + timestamp), decrementing the Play Balance. Recorded directly in this app, independent of Timing and the Manual Sync.
_Avoid_: Spend, consumption

**Play Balance**:
The current total available to spend: Timing-Derived Earned Total (itself already net of any Draining Activity) + Manual Sync − sum of Playtime Used. Accumulates indefinitely for now (a future cap is a known possibility, not yet designed). Shown only behind a debug-only reveal on the dashboard (triple-tap the joystick icon) — the primary hero figure is Playtime, below. Always equal to Playtime's Today's PT + Reserve — a pure decomposition of the same total, nothing added or dropped.
_Avoid_: Balance (ambiguous outside this context), credit

**Playtime**:
The dashboard's primary hero figure: Today's PT + Reserve. Unclamped — can go negative if usage has outpaced earnings, and as of [ADR-0012](docs/adr/0012-persisted-entry-consumption-ledger-with-window-bounded-spending.md) this happens more readily than before, since a spend can no longer fall back on Backlog once today's and Reserve's in-window entries run dry. Distinct from Play Balance (above), which is the same total computed a different way and normally hidden. Also exactly equal to This Week's Earned minus This Week's Used plus Pushscroll Balance (see This Week) — a second, independent decomposition of the same number, shown alongside the hero figure specifically because it needs no explanation of flooring or causality to verify by eye, unlike Today's PT + Reserve.

**This Week**:
The Entry Expiry Window's raw (non-ledger) totals: every entry within the last 7 days' original minutes summed, split by Effect into "Earned" (positive Activities) and "Drained" (Draining Activities), and every Playtime Used record within the same window summed ("Used"), each with no consumption/FIFO logic applied. Earned is kept gross rather than netted against Drained, so a week of 300 earned against 280 drained reads as exactly that rather than as "20m earned". Shown per-Activity (gross earned only, since Playtime Used draws from one global pool, not a per-Activity one — see Playtime Used) and as a whole-User total alongside Today's. `This Week's Earned − This Week's Drained − This Week's Used + Pushscroll Balance == Playtime`, holds for almost every spend logged after [ADR-0012](docs/adr/0012-persisted-entry-consumption-ledger-with-window-bounded-spending.md) — since a spend can no longer draw on Backlog (below), there's no third term needed to reconcile the identity the way Backlog Drawn used to be required (removed by ADR-0012, which superseded [ADR-0011](docs/adr/0011-surface-backlog-remaining-alongside-backlog-drawn.md)). One known gap: an entry can still age out of the window, from a *later* read's perspective, after funding a usage that itself is still within window at that read (an entry is always at least as old as the usage it funded) — Backlog Drawn used to paper over exactly this, and ADR-0012 dropped it deliberately (KISS) rather than replace it, so the identity is a sanity check, not a hard invariant.

**Backlog**:
Play Minutes earned but never spent before aging out of the Entry Expiry Window — as of [ADR-0012](docs/adr/0012-persisted-entry-consumption-ledger-with-window-bounded-spending.md), permanently unspendable once there, a hard "use it in a week or lose it" rather than a hidden-but-reachable cushion. Not surfaced anywhere in the UI (ADR-0012 removed the Backlog Drawn/Backlog Remaining dashboard figures that used to show it) — it exists only as the reason Reserve and Playtime can go negative more readily than before, once today's and Reserve's in-window entries run dry.
_Avoid_: Backlog Drawn, Backlog Remaining (both removed by ADR-0012 — a spend can no longer reach Backlog at all, so neither figure has anything left to describe)

**Today's PT**:
The "today" component of Playtime: the sum of today's entries' `remaining` balance (Entry Consumption Ledger, local calendar day per [ADR-0005](docs/adr/0005-local-timezone-for-day-boundaries.md)) after the day's own Playtime Used has drawn against it. Resets to just today's activity every local calendar day, with no exceptions — Pushscroll Balance lives in Reserve instead (see below), since it has no day boundary of its own to reset by. Unlike Playtime, this is never negative, for two reasons: a spend consumes today's own entries first and only *overflows* into Reserve once they're exhausted (see Reserve), so there's nothing left on today's entries to go negative; and a day whose Draining Activities outweigh its earnings is floored at 0, with the excess drain spilling into Reserve instead ([ADR-0013](docs/adr/0013-draining-activities-outside-the-consumption-ledger.md)) — the same direction spend overflow already travels. Which of the two absorbs the shortfall doesn't change Playtime, since it's their sum.

**Reserve**:
Play Minutes earned but not yet spent, that aren't scoped to today: prior-days' User Displayed Total (itself already net of spending, via the Entry Consumption Ledger) *plus* the current Pushscroll Balance (a Manual Sync value, above), *minus* any unmatched overflow — spend, from any day, that exceeded every entry available at the moment it was logged, once the ledger's draw-down has nothing left to charge it against. "Available" means today's entries and Reserve's own in-window entries only — as of [ADR-0012](docs/adr/0012-persisted-entry-consumption-ledger-with-window-bounded-spending.md), Backlog is never reachable, so this overflow triggers considerably more easily than it used to (previously, overflow only occurred once Backlog itself ran out too). Pushscroll Balance is grouped here rather than with Today's PT because both share the same shape — carried-over credit with no day boundary of its own — unlike Today's PT, which resets every midnight. Can still go negative overall (if Pushscroll Balance itself is negative, if a day's overspend overflows past everything available, or if a day's drains exceed its earnings and spill down here — see Today's PT), but never negative *purely from expiry*, since expiry only removes minutes already known to be unspent. Shown as its own dashboard widget, separate from Today's PT, so today's activity and carried-over history stay visually distinguishable even though they combine into a single spendable Playtime number.
