# Draining Activities, kept outside the Entry Consumption Ledger

**Status**: accepted

Some tracked time should cost Play Minutes rather than earn them — watching YouTube is the motivating case. We're adding **Draining Activities**: an Activity whose **Effect** is negative, whose Timing entries subtract from the balance instead of adding to it. They're created and edited through the same UI as any other Activity, and they flow through the same Timing fetch, the same Entry Expiry Window, and the same per-Activity dashboard breakdown.

`Effect` is stored, not derived. `activities.multiplier` becomes an unsigned magnitude and a new `activities.effect` column (`"positive"` / `"negative"`) carries the direction. The alternative — a signed `multiplier` with Effect derived from its sign — was rejected because the *entry* representation is already `effect` plus an unsigned magnitude (a drain must never be representable as a negative `remaining`, see below), so a signed Activity would put a translation seam between Activity and entry, doing `abs/1` and a sign test, at exactly the point where this feature's sharpest failure mode lives. Storing Effect makes the concept one shape end to end: `EntryLedger.build_entries/2` copies `effect` through and multiplies by a magnitude, with no sign arithmetic anywhere. It also turns the "0× is meaningless" validation into `multiplier > 0` (a DB check constraint) rather than `multiplier != 0`, and makes ADR-0013's confirmation trigger (below) an equality test on `effect` rather than a comparison of two floats' signs. There is no derived-data consistency risk in storing it, because nothing else encodes the direction — `multiplier` is a pure magnitude, not a second copy.

A drain **never enters the Entry Consumption Ledger**. Its entry is built like any other, carries an unsigned `play_minutes` and a `remaining` equal to it, and is simply summed *negatively* into Today's PT and Reserve. It is never consumed, never drawn down, and never produces an `EntryConsumption` row. This preserves ADR-0012's central property — the ledger is written only by `PlayBalance.log_spend/6`, at spend time — which a drain would otherwise violate, since Timing entries appear asynchronously with no write moment of their own to settle against. The rejected alternative (below) modelled a drain as a synthetic spend consuming positive entries FIFO; it would have given per-entry attribution ("this YouTube session ate Monday's coding minutes") at the cost of settling consumption *at read time*, a write-on-read that races every Timing back-fill.

Because `remaining` is unsigned, `EntryLedger.consume_pool/4`'s existing `remaining > 0` predicate no longer excludes drains the way a negative `remaining` would have. The guard is therefore explicit and lives at **pool construction in `log_spend/6`** — the pool is filtered to `effect == :positive` before `with_remaining/2` — so `replay/4` and `consume_pool/4` keep their existing contract ("everything you are given is consumable") unchanged. Without that guard a spend would consume a drain, shrinking the penalty *and* booking the spend as funded: two errors compounding in the same direction, with no crash and no failing test. This is the single most important invariant in this ADR and is covered by a named test.

Drains expire symmetrically: a drain leaves the Entry Expiry Window after 7 days like any other entry, and since nothing ever draws it down it sits at full weight for that whole time and then vanishes. A bad week is behind you in a week — the same "use it or lose it" rule read backwards. The consequence is accepted deliberately: a drain can be waited out rather than worked off.

Today's PT stays floored at 0. When a day's drains exceed its earnings, the excess spills into Reserve, mirroring the direction spend overflow already travels. `playtime = today_net + reserve` is unaffected by the attribution either way, and "Today's PT resets fresh every local day and is never negative" survives as a rule — now because of the floor rather than because of the two-pass draw-down.

Drains apply retroactively across the whole trailing window, consistent with how positive Activities already behave (Activated At is not load-bearing for user-facing figures — ADR-0008, and CONTEXT.md's User Displayed Total). Mapping a Timing project as draining can therefore deduct several hours the instant it's saved, so the UI confirms the projected hit — but only on an Effect *crossing* (an Activity becoming draining, whether created that way or edited into it), not on every deepening of an existing drain. Confirming every adjustment would train the user to click through the one confirmation that matters.

## Considered options

- **Model a drain as a synthetic spend** that FIFO-consumes positive entries through the existing ledger. Rejected: it needs consumption settled on the read path, which is exactly the invariant ADR-0012 established, and it would have to re-settle whenever Timing back-fills or edits an entry. The aggregate balance is provably identical either way — the difference is only per-entry attribution, which isn't worth a write-on-read.
- **Let drains reduce the pool a spend can draw from** (netting them against the pool inside `log_spend/6`). Rejected for the same reason the totals are identical: it changes only how the shortfall is attributed between `remaining` and `deficit`, at the cost of making the write path aware of a concept it otherwise never needs. The visible consequence is accepted: Today's PT can read 0 (floored) while a spend still succeeds against today's positive entries.
- **Drains never expire**, persisted permanently like `deficit`. Rejected: the Timing fetch is window-bounded as of ADR-0012, so this reintroduces the unbounded history that ADR removed, for a rule the symmetric version already expresses.
- **Drains expire only once "paid off"** (forgiven only if their window ended net-positive). Rejected: it can't be stated in one sentence, and it makes expiry depend on aggregate state rather than on a single entry's own age.
- **Make Activated At load-bearing for draining Activities only**, so a new drain never reaches backwards. Rejected in favour of a visible confirmation: an asymmetric rule is one every future reader of the ledger has to hold in their head, whereas the shock is fully addressed by showing the number before it lands.
- **Derive Effect from a signed `multiplier`**, with `ActivityManager.effect/1` as the single named accessor. The strongest rejected alternative — it needs no migration and leaves the `Persistence` contract untouched. Rejected for the representation seam described above.

## Consequences

- **Every `× activity.multiplier` site becomes a silent-positive bug until made Effect-aware.** With `multiplier` unsigned, a drain computes as a gain, with no crash to point at it. Rather than correcting each site independently, the Effect-to-arithmetic mapping has exactly one definition, as two private functions in `PlayBalance`:

  ```elixir
  # The single place an Effect becomes a sign (ADR-0013).
  defp apply_effect(magnitude, :positive), do: magnitude
  defp apply_effect(magnitude, :negative), do: -magnitude

  defp play_minutes(activity, minutes),
    do: apply_effect(minutes * activity.multiplier, activity.effect)
  ```

  `play_minutes/2` replaces the three `minutes * activity.multiplier` expressions in `activity_today_minutes/2` (`play_balance.ex:122`), `week_activity_minutes/4` (`:169`), and `sum_totals/3` (`:385`, which feeds the debug-only Timing-Derived Earned Total). `apply_effect/2` alone covers the entry-summation sites, `sum_play_minutes/1` and `sum_remaining/1`, since an entry already carries its magnitude and its `effect`. No new module and no new public API: all six call sites are implemented inside `play_balance.ex`, so both functions stay private.

  The fourth `× multiplier` site, `EntryLedger.build_entries/2` (`entry_ledger.ex:176`), deliberately does **not** use this and stays exactly as written — an entry stores an unsigned magnitude plus its `effect`, so `build_entries/2` copies `effect` through and applies no sign at all. Two further sites merely render the multiplier for display and need it labelled rather than signed: `dashboard_live.html.heex:416` and `Mix.Tasks.Balance.Snapshot` (`balance.snapshot.ex:179`).

  A signed `multiplier` would have made all of these correct for free, needing neither these functions nor `log_spend/6`'s `effect == :positive` guard; that is the accepted cost of the stored-Effect representation.
- The `Persistence` plugin contract gains `:effect` on Activity create/update and read, which means matching changes in the Stub, the Sqlite adapter, and `persistence_contract_case.ex` — a cost paid once per backend, including any future Fibery backend (ADR-0001).
- A migration adds `activities.effect` (`null: false`, default `"positive"`) and makes `multiplier` unsigned. The backfill is safe regardless of current data — `effect = CASE WHEN multiplier < 0 THEN 'negative' ELSE 'positive' END, multiplier = abs(multiplier)` — which also cleans up any negative row that slipped in through the add-form, currently unvalidated (`activity.ex:18-24` casts and requires `multiplier`, with no `validate_number`).
- `multiplier` gains a `> 0` validation. 0× is refused outright: an Activity that neither earns nor drains is noise on the dashboard.
- `PlayBalance.Today` gains `week_drained` (and the equivalent for today), keeping `week_earned` gross-positive. The hero card's reconciliation line becomes `earned − drained − used + Pushscroll Balance`. Folding drains into `week_earned` would have kept the identity intact but made the line unreadable — a week of 300 earned against 280 drained would display as "20m earned this week", defeating the reason that line exists.
- The multiplier stepper (`dashboard_live.ex:276`) keeps its `max(0.0)` clamp, which is now correct rather than incidental — direction moves to an explicit positive/negative toggle beside it, so the sign is a deliberate choice rather than something you step past through a meaningless 0.0.
- The `playtime == week_earned − week_drained − week_used + pushscroll_balance` identity holds to exactly the same approximation as before; ADR-0012's known gap (an entry aging out after funding a still-in-window usage) is unchanged by drains, since drains never fund anything.
- `deficit` is unchanged (`total_used − total_consumed`): drains are never consumed, so they never contribute a consumption row and never appear in either term.
- `CONTEXT.md` gains **Effect** and updates **Activity**, **Multiplier**, **Play Minutes**, **Today's PT**, **This Week**, and **Play Balance**.
- Presentation decisions are deliberately left out of this ADR — they're cheaply reversible and don't meet the bar: a 100%-stacked horizontal distribution bar above the Activities list, shaded on a fixed ±3× ramp (deepest at |3×| and beyond, clamped), earners grouped before drains and descending by share within each group, net Play Minutes printed alongside, sign carried by a `+`/`−` label as well as by hue, and a light Effect tint plus red/green signed figures on each Activity card.
