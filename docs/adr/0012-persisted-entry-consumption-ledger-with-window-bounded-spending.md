# Persisted Entry Consumption Ledger, with spending bounded to the 7-day window

**Status**: accepted

`PlayBalance.compute_today/4` filters `usages` to the last 7 days before replaying them against entries (`EntryLedger.replay/4`) — safe for in-window figures (a usage older than the window can't have touched an entry still inside it, by causality), but not for `backlog_remaining`: once a usage itself ages past 7 days, its consumption is dropped from every future replay, and any entry it drained reappears with its full original balance. This compounds weekly and was never caught by a test — confirmed by a repro showing a fully-spent 8-day-old entry reporting `backlog_remaining: 100.0`, its whole original amount, as if never touched.

We're replacing live replay with a persisted `EntryConsumption` ledger: a sparse table, one row per (`activity_id`, `time_entry_id`) *only once that entry has been drawn on*, holding cumulative Play Minutes consumed. Untouched entries have no row — `remaining` is `entry.play_minutes` by absence, still derived live from Timing, same as today. `PlaytimeUsed.log_usage/2` becomes the single write path: it performs the FIFO draw-down at spend time and persists the debit immediately, instead of deferring to a later live replay that can forget it. Consumption is stored in Play Minutes, frozen at spend time — not raw Timing minutes — since `PlaytimeUsed` is already an immutable absolute figure; storing consumption any other way would let a later Multiplier edit silently rewrite what a settled spend actually represented. An entry's *total earned* stays live-derived from the Activity's current Multiplier as always; only the *consumed* portion is locked in.

Alongside this, we're deliberately narrowing what a spend can reach: going forward, a spend draws only on today's entries plus Reserve entries still inside the 7-day Entry Expiry Window — never on backlog. If that's insufficient, it registers as `deficit` (Reserve/Playtime goes negative), the same mechanic that already exists for genuine overspend, just triggered far more easily now that there's no backlog cushion behind it. An entry that ages out unspent becomes permanently unspendable — a hard "use it in a week or lose it," not the previous "hidden but still reachable" model. This is a stronger decay than ADR-0010 originally introduced, chosen deliberately over a partial-cushion alternative.

This reverses `backlog_remaining`'s entire premise (ADR-0011: "this is what a spend draws on, silently, once it exceeds everything Reserve visibly shows"). Since backlog can no longer be drawn on at all, `backlog_drawn` and `backlog_remaining` are removed from `PlayBalance.Today` and the dashboard entirely, rather than relabeled — this ADR supersedes ADR-0011.

A one-time backfill migration seeds `EntryConsumption` by replaying full history under the *old* unbounded-overflow rule (so historical spends that genuinely drew on backlog stay accurately recorded as having done so) — only usages logged after cutover obey the new window-bounded pool. This corrects the existing inflated backlog figure back down to what's actually true, once, rather than only stopping it from getting worse.

## Considered options

- **Minimal fix: stop dropping old usages from replay, keep everything live-recomputed** — considered first as the smallest change that fixes the actual bug (replay against full unbounded usage history, same as entries already are). Rejected in favor of persistence: replay cost would grow unboundedly with lifetime usage count, and it doesn't address the separate, deliberate decision to stop spending from reaching into backlog at all.
- **Push consumption into Timing itself**, via `billing_status` (`billed`/`paid`) or a `custom_fields` entry, since Timing entries have a stable `time_entry_id` and both are writable through the Timing API. Rejected: `billing_status` can only express whole-entry state, not the partial per-entry consumption FIFO draw-down requires, and repurposing it risks colliding with a User's real invoicing use of that field. `custom_fields` would work in principle but makes every spend depend on a reliable network write-back to an external system, a new partial-failure mode this app doesn't currently have anywhere.
- **Mirror every fetched entry into the local table**, not just consumed ones — rejected in favor of the sparse table; entries nobody's spent against are already correctly computed live from Timing, and don't need a local copy.
- **Validate/reject a spend that exceeds the window-bounded pool**, rather than letting it register as `deficit` — rejected; `deficit` is the existing, already-understood mechanism for this, and rejection would be a new validation path and failure UX nothing so far has asked for.
- **Relabel `backlog_remaining` as an informational "expired, unspent" figure instead of removing it** — rejected at the User's explicit preference (KISS): once it can't inform "how much cushion do I have," it stops earning its place on the dashboard.

## Consequences

- The Timing adapter (`lib/timing_play_time/plugins/time_source/timing.ex`) needs to start capturing `entry["id"]` — `dated_entry/1` currently discards it, since nothing needed entry identity before this.
- `EntryLedger.replay/4`'s window-bounded draw-down logic is reused for both the live write-time consumption in `log_usage/2` and the one-time backfill script — the two differ only in whether the pool is bounded to the window (new spends) or unbounded (backfill, matching the old rule).
- `CONTEXT.md`'s Entry Consumption Ledger, Backlog Drawn, Backlog Remaining, and Reserve entries all need updating: consumption is no longer purely recomputed-live, and Reserve no longer has a backlog safety net behind it.
- The `playtime == week_earned - week_used + backlog_drawn + pushscroll_balance` reconciliation identity (ADR-0010) loses its `backlog_drawn` term along with the field itself; the identity simplifies to `playtime == week_earned - week_used + pushscroll_balance` for any usage logged after cutover, since backlog can no longer silently absorb overflow.
- `PlaytimeUsed` has no update or delete today, only `log_usage`/`list_all`/`total_used*` — persisted consumption never needs a "reverse this spend" path, because nothing in the app can currently un-log a usage.
