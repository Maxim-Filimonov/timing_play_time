# Optional email linking via Auth0 passwordless login

**Status**: accepted

Cashes in the option [ADR-0006](0006-multi-tenant-anonymous-cookie-accounts.md) explicitly deferred rather than ruled out: "real accounts can be layered in later if the loss-of-access failure mode becomes a real problem, without changing the underlying tenant-isolation shape." That failure mode — losing the session cookie means unrecoverable loss of a User's data, and there is no way to reach the same User from a second device — is now worth fixing for the owner and a small known group. It is **not** worth building public signup for. So this adds an **optional** email link: a User may attach one verified email, and someone arriving without a usable cookie may sign in with that email to get their existing User back. `users.id` (binary_id) stays the sole identity; nothing foreign-keys to email; anonymous-first onboarding is unchanged — first visit still silently provisions a User (`Plugs.CurrentUser`), and email linking is opt-in from Settings.

Auth0 is a **credential gate, not a session**. It verifies an emailed one-time **Login Code** and hands back an OIDC identity (`sub` + `email` claims); the app then sets its **existing `Plug.Session` cookie** exactly as ADR-0006 already does — same encrypted, HttpOnly, SameSite=Lax, fixed ~1-year `max_age` config, untouched. Auth0 is contacted **only** during the link and sign-in flows: never on an ordinary request, never in `Plugs.CurrentUser`, never in `LiveAuth`'s mount path. There is no token storage, no refresh, no per-request token validation. The integration is a plain server-side OIDC authorization-code redirect via [`oidcc`](https://hex.pm/packages/oidcc) (BEAM-native, OpenID-certified, actively maintained by the Erlang Ecosystem Foundation) — **not** `ueberauth_auth0` (last release 2022, effectively unmaintained), and not `oidcc_plug`'s plugs, since the app tracks its own `state`/`nonce`/PKCE verifier through the `IdentityProvider` behaviour (ADR-0002) rather than through `oidcc_plug`'s own session handling. Code entry happens on **Auth0's hosted Universal Login page**; the app builds no code-entry screen, only a redirect out and a callback route in.

The join key is **`auth0_sub`**, a new unique nullable column — an opaque `email|<hex-id>` string minted once at Auth0 user-creation and immutable for that record's life. `email` is stored beside it as a **denormalised display copy only, never used for lookup**, re-synced from the ID-token claim on each login. Auth0 does not support changing the email on a passwordless-email identity: a different address is a different `sub`, hence — under the collision policy below — a different User. There is no in-place email-update path, and v1 has **no in-app unlink and no in-app change-email**; Settings shows only a read-only masked status line once linked.

Collision policy is **switch, never merge**. On a successful sign-in the session cookie is rewritten to the authenticated User. The anonymous User the current browser was just provisioned is **hard-deleted only if provably empty** (no Activities, Integration, Playtime Used, or Manual Sync) **and it is not the User being signed into** (signing into your own already-linked, still-empty User must not delete the account you're signing into); otherwise it is left orphaned and unreachable, never destroyed silently. Two Users' data is never merged. Linking an email (or `sub`) already attached to another User is **refused**, not transferred; and a link-flow callback that returns a *different* `sub` for a User that is already linked is refused too. Only the **passwordless email** connection is enabled on the tenant — no social, no username-password — because a second connection would mean a second `sub` for one human, re-creating the collision permanently. A **code, not a magic link**: the flow's whole purpose is cross-device, and a link mailed to a phone opens on the phone (the device you are signing in *from*, not *to*), whereas a 6-digit code is transcribable across devices.

**Environments.** The anonymous path never touches Auth0 in any environment. **Test** selects a stubbed adapter (behaviour + stub, per [ADR-0002](0002-microkernel-plugin-architecture.md)'s existing plug-in pattern) in `config/test.exs` only — never dev, never prod. **Dev** uses a real Auth0 dev tenant (`scripts/auth0-dev-setup.sh`). Accepted trade: the login flow specifically cannot be developed or run offline.

## Considered Options

- **Hand-rolled login codes** — generate a 6-digit code, email it via the app's own mailer, store a short-lived hashed challenge, verify it in a LiveView. No third-party dependency and no "cannot develop offline" cost. Rejected: it re-implements what Auth0's passwordless connection gives for free (code generation, delivery, 3-minute expiry, last-issued-only, 3-attempts-then-reissue, rate limiting, deliverability/reputation) and puts the app in the business of sending transactional email — a whole operational surface (Mailgun/SES, bounces, SPF/DKIM) this app has so far avoided. The credential-handling code would be security-sensitive and entirely ours to get right.
- **Auth0 as the session** — keep the Auth0 access/ID token, validate it per request, refresh it, treat "logged in to Auth0" as the app's auth state. Rejected: it discards ADR-0006's cookie model for no gain. The app has exactly one thing it needs from Auth0 — proof that this human controls this email, once, at link time — and nothing about ordinary requests improves by threading a token through them. It would also make every request depend on Auth0 availability, violating the "gate, not session" line above.
- **`ueberauth_auth0`** — the strategy library Auth0's own Phoenix quickstart uses. Rejected: last release 2022-10-27, last commit 2023-01-29, open issues and PRs unattended. Pinning identity infrastructure to a dormant dependency when a certified, actively-maintained generic OIDC client (`oidcc`) does the same job is a poor trade.
- **In-app (embedded) code entry** via Auth0's Authentication API (`POST /passwordless/start` + the `passwordless/otp` grant). Rejected for v1: the app would own the code-entry screen, resend control, and every error state, and it does not go through the OIDC `/authorize` redirect, so it fits neither `oidcc` nor the "plain redirect" framing. Kept in the back pocket only if product later insists users never leave the app's own pages.
- **Merge two Users' data on collision** — when someone signs in and the current browser's anonymous User already has Activities, fold them into the authenticated User. Rejected: merging tenant data (deduping Activities, reconciling two Play Balances and consumption ledgers) is a hard problem with no obviously-correct answer, well beyond what "recover my account" needs. Switch-and-orphan is unambiguous.
- **Enable a username-password connection alongside passwordless** so a user has a fallback credential. Rejected: two connections means two `sub`s for one human, hence two Users — the exact collision this design works to avoid, made permanent.

## Consequences

- **There is still no logged-out state — and that is now a surprise rather than an obvious fact.** Clearing the session cookie does not yield a login screen; `Plugs.CurrentUser` silently provisions a *fresh, empty* User exactly as it does today, and the dashboard renders for that new User. Someone who has linked an email and then clears their cookie lands on an empty dashboard, not a "sign in" page. This is mitigated, not removed, by a dismissible arrival banner (below) shown while a User looks new. Any future reader of the auth code needs to hold this: "no cookie" and "not logged in" are not the same thing here, and the app never refuses to serve a request for lack of identity.
- **New migration** on `users`: `auth0_sub` (string, nullable, unique index), `email` (string, nullable, unique index — SQLite treats NULLs as distinct, so many anonymous Users coexist), `arrival_banner_dismissed` (boolean, `null: false`, default `false`). No column is ever made non-nullable; no existing row needs backfilling (an unlinked User has both identity columns `NULL`). The pre-existing default User from ADR-0006's backfill migration is just another unlinked User and needs no special handling.
- **New plug-in point** (ADR-0002): an `IdentityProvider` behaviour with a real `oidcc`-backed adapter and a `Stub`, selected by `config :timing_play_time, :identity_provider_adapter`. Config default is the real adapter; `config/test.exs` overrides to the Stub. The behaviour is the seam the "cannot develop offline" cost is confined to.
- **`oidcc` provider-configuration worker** joins the supervision tree in dev/prod only (the Stub adapter starts nothing), reached through `application.ex`'s existing `supervised_adapter_children/1` mechanism (matched on `child_spec/1`, not `start_link/1`, so both GenServer-based and plain adapters with their own child spec are picked up). Its `backoff_type` must be a non-`:stop` value so the app still boots when Auth0's `.well-known` document is unreachable at startup — the Link / Sign-in buttons then yield the generic failure (below) until a retry succeeds. `oidcc` exposes no clock-skew leeway, so the app host must run NTP; skew surfaces as the generic failure.
- **New env vars**, read in `config/runtime.exs`: `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, `AUTH0_CALLBACK_URL`. Dev loads them from a gitignored `.env` (via `dotenvy`); prod via `fly secrets set`. Absent in test (the Stub needs none). CI is unaffected — it runs the test suite (Stub) and `flyctl deploy`.
- **One generic failure outcome** for the entire redirect round-trip. Auth0 unreachable at click, user abandons the hosted page, any callback `error`, token-exchange / `state` / `nonce` / clock-skew failure, **and** a valid `sub` that maps to no User row — all return to the origin page (Settings for link, dashboard for sign-in), flash *"That didn't complete. Please try again."*, persist nothing, change no cookie, delete no User. No per-error-code copy. `error_description` is unstable Auth0 text and must never drive UX; `state` mismatches are logged at warning and the callback is not processed.
- **The flow is stateless across the redirect.** The app persists nothing when it sends the user to Auth0; the only transient state is `%{flow, params}` (the OIDC `state` + nonce + PKCE verifier, and a `link`/`login` flag) kept in the Plug session under the `:auth` key, self-consumed on callback. Consequently there is no "link started / unverified" state to show, no expiry rule, and no cleanup job. The callback route **processes then redirects, and never renders** — back/forward/refresh cannot strand the user on a spent-code URL.
- **Two Settings states collapse to a masked read-only line.** Once linked, Settings' new "Sign-in & devices" section shows `m•••n@example.com ✓` with fineprint that change/remove is not available, plus the switch-account control. States: `anonymous` / `linked` / `email-taken-refused` (transient, flash-only).
- **A per-User arrival banner.** While a User is empty (0 Activities *and* no Integration — the cookie-less-arrival signature), a dismissible banner sits above the Playtime hero on the dashboard offering *Sign in to recover a Playtime you started elsewhere* and *I'm new — hide this*. Dismissing sets `arrival_banner_dismissed`. Once the User has any data the banner never shows again.
- **Switch-account confirm dialog** leads with *"Your current play time isn't deleted."* — steering an unlinked user to link first, reassuring a linked one.
- **`Plugs.CurrentUser` and `LiveAuth` logic is unchanged.** The callback controller writes the new `:user_id` into the session and redirects; the next request flows through `CurrentUser` normally. Neither module learns anything about Auth0.
- **The Endpoint session config is untouched** — same salts, `same_site`, `max_age`, `secure` gating as ADR-0006.
- **`CONTEXT.md` changes**: the **User** entry's "there is no login, password, or email" clause becomes false and is rewritten; *Avoid: Account* stays but its rationale is reworded (the tenant boundary genuinely does not change — but "no login credential exists" no longer holds). New glossary entries: **Linked Email**, **Login Code**.
- **Enumeration exposure is inherent and accepted.** Under Universal Login, Auth0 emails the code unconditionally — the app has no "if that email is linked, we sent a code" branch to make, because the app sends no mail. Accepted under the owner-plus-small-group scope; "Disable Sign Ups" stays **off** on the connection (on breaks first-time linking and buys nothing in a hosted flow), and there is no Pre-User-Registration Action. The real gate is the callback logic: it only ever links to the User you already are, or switches to an existing linked User — it never mints an app User from a bare Auth0 signup.
- **Orphaned non-empty anonymous Users accumulate** in the DB over time (switch-never-merge leaves them). Housekeeping and observability for that are deliberately deferred — not designed here.
